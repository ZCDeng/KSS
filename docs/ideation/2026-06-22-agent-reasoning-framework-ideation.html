要不要给 KSS 塞一个 Agent 推理框架?

选题盘点 · 2026-06-22 · ce-ideate(聚焦版) · 基于代码实证,非计划承诺
一句话结论:不需要"自主 agent 框架",需要的是三块薄层。
KSS 的 agent 底座已经搭好了 —— MCP parity(13 tool)、LLM 在管线里有实职、数字/注入双纪律。 真正缺的不是"让 AI 自己决策的回路"(那条线你有意不做),而是:(1) 让 agent 一次调用就吃透代码与数据的自描述层; (2) 用固定剧本而非自主循环换便利性;(3) 把 agent 从「只有 Claude Code 能用」搬进 KSSDeck 给真实用户用。 边界其实已建了 90%(read/paper/live 三档 + confirm),只差把它写成 agent 自知的红线。

题面分解(5 轴): A 推理回路形态 · B 便利性增量 · C 边界红线 · D 自我描述(吃透) · E 可验证

三个子问题的直接回答

① 有必要塞 agent 推理框架吗? —— 不必要塞重的。 Claude Code + 你的 MCP 本身就是推理回路了。 再叠一个 LangGraph/AutoGPT 式自主 loop,边际价值低(回路已存在)、风险高(逼近"替用户做买卖判断"的红线)。 真正的 ROI 在"让现有 MCP 面更易被 agent 理解"和"一层薄编排",不在"造自主大脑"。

② 边界怎么定? —— operator / explainer,永不做 decider。 Agent 能查、能解释、能跑 paper 任务、能解释为什么某只上榜; 不能下单、不能给个性化买卖建议。底层 _LIVE + confirm=True 三档闸已在,缺的是把这条线写进 system prompt + 输出守卫,并让 agent 自知所处档位。

③ 怎么快速吃透代码库 + 数据库? —— 一次调用拿到"定向包"。 现在 agent 要读 AGENTS.md + 调 get_snapshot + 调 list_cron + 猜 parquet 列名才上手,且没有任何数据字典/catalog。 答案是自动生成的数据目录 + 一个 get_orientation 入口工具(能力图 + 数据目录 + 新鲜度 + 文档指针,一次返回)。

留存创意(按价值排序)

#1自动生成的数据目录(data catalog)轴 D · 数据库

从代码反射出全量数据资产字典:每个 parquet/cs_data_*.csv/*.db 的列名 · 含义 · 粒度 · 刷新源 · 最近日期。 当前零目录 —— agent 只能 grep pipeline 脚本去猜列名。这是"吃透数据库"的根。

  • 实现:introspect bridge 的 read 函数 + 读 parquet schema + 扫 storage/ 目录,产出 storage/data_catalog.json,由一个 launchd 任务每日刷新,永不漂移。
  • 对比手维 doc:手维必烂。自动生成才是对的那套(冲突暴露不折中)。

成功标准:新 agent 不读任何 pipeline 脚本就能正确回答"margin_daily 里有哪些字段、几号的数据"。 · 工作量 低

#2get_orientation —— 一次调用的"定向包"轴 D · 代码库

一个 MCP 入口工具/资源,单次返回:dispatch 命令图 + run_task 白名单 + 数据目录(#1) + 各 cron 新鲜度 + 关键文档指针(AGENTS.md / ai_native_surface_assessment.md)。 把"读 4 处才上手"压成"1 个工具调用上手"。

成功标准:冷启动 agent 第一个工具调 get_orientation 后,后续查询零误调(不再调不存在的 tool/列)。 · 工作量 低 · 依赖 #1

#3有界编排剧本(复盘 playbooks),取代自主 loop轴 A·B·C

"框架"= 剧本注册表,不是 LangGraph。把高频多步任务固化成确定性 DAG,agent 只选剧本不自由发挥。 例:解释为什么这只今天上榜 = get_stock → get_sector_rotation → get_discovery_candidates → get_report 串成一条。

  • 便利性来自"一句话触发一条复盘链",而非让模型自己想步骤(省 token、可复现、可测)。
  • 路由/串接由代码做,模型只做"选哪条 + 解释结果"的判断类任务。

成功标准:3-5 条最高频复盘问题各有一条剧本,端到端可复现,有 golden 测试。 · 工作量 中

#4KSSDeck 内置 agent 面板 —— 把 agent 给真实用户轴 B · 便利性主增量

当前 agent 只有开 Claude Code 的开发者能用。真正的"用户便利性"是在桌面 app 里放一个 chat-with-tools 面板: 复用 MCP 读 tool + 数字纪律,用户用中文问"今天北向在买啥板块",app 调工具 + 代码渲染真值答。

  • 这是 agent parity 从"原则"走到"终端用户能摸到"的那一步。
  • 读优先(#5 边界守卫兜底);写/跑任务走已有 confirm 闸。

成功标准:非技术用户不开终端,在 KSSDeck 里完成一次带真值的盘面问答。 · 工作量 高 · 依赖 #2 #5

#5把"operator 不 decider"红线工程化轴 C · 边界

三档能力(read 恒开 / paper-write 需 confirm / live 需 env+confirm)已在代码里。缺的是: (a) system prompt 显式声明"不给个性化买卖判断";(b) 输出守卫 —— 检出"建议买/卖/仓位"措辞即 fail-loud 中和(复用 U7 风格);(c) agent 自知当前档位。

成功标准:诱导 agent 给个股买卖建议时,稳定被守卫拦截并记日志。 · 工作量 低

#6Agent 论断的来源纪律(provenance)轴 E · 可验证

把 U7 的"数字必由代码渲染"延伸到 agent 自由输出:agent 陈述的每个量化结论须挂数据源/字段指针,无源的数字检出即中和。 让"agent 解释"可审计,不退回幻觉。

成功标准:agent 答案里每个百分比/金额可点回 catalog 里的某字段+日期。 · 工作量 中 · 与 #5 同机制

#7(later·门控)接通 eval-ledger 只读喂给推理轴 E

决策账本 ledger.db 已在,但 plan 把 eval 回路 deferred(要 U7 跑稳 2-3 周)。一旦开,agent 解释可引用已结算的历史命中率, 让"为什么看好"有回测背书,而非纯叙事。现在不做,等数据门解锁。

成功标准:paper_trade 攒够去重日 → agent 能引用某剧本的历史 IC/胜率。 · 工作量 中(被数据门控)

否决的方向(附理由)

✗ 完整自主 agent loop(LangGraph / AutoGPT 式自决策 + 迭代)

逼近"替用户做买卖判断"的有意红线;重;且 Claude Code 已是回路 —— 边际价值低、风险高。这正是 assessment doc 里"既没做、也不打算做"的那块。

✗ 自然语言 → tool 路由层

冗余。MCP 客户端(Claude)本身就做 NL→tool 路由,再造一层是重复造轮子。

✗ 在 commentary.py 里给 LLM 开 tool-calling

commentary 是批处理,"一次 prompt + 代码补真值"是有意设计(U7 关掉的就是数字幻觉)。在这里加 tool-use 会把刚关上的风险重新打开。

建议的下一步

最小可行起点 = #1 数据目录 + #2 定向包(都低工作量、零红线风险、直接答"快速吃透"), 跑通后再上 #3 剧本 把便利性兑现。#4 内置面板是大件,值得单开一次 ce-brainstorm 定清楚范围。 "自主框架"本身 —— 建议明确不做。
