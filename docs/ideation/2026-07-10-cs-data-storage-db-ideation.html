日线「停在 6 月」现象 → 是否升级数据库？

2026-07-10 · topic: cs-data-storage-db · mode: repo-grounded · focus: 从 git 冲盘 / 自选图陈旧分析是否上库
结论先说：仅凭这次现象不必为了「别被 git 冲掉」去上数据库——根因是跟踪态 + checkout，不是 CSV 存不了数。 上库有独立价值（新鲜度契约、多读路径一致性、查询），但应另立目标，不要把运维事故当成架构刚需。 当前正确第一刀（已做）：cs_data_*.csv 脱钩 + 只保留日更/cron 写盘。

Grounding Context

现象链：自选图读 detail.history ← bridge 读 cs_data_<code>.csv；文件末日期停在 2026-06-26 → 图停 6 月。日更曾拉到 7 月，随后 git checkout -f 把已跟踪的 ~102 个 csv 还原成仓库种子。

规模：约 115 只池子、合计 ~14MB 行数级 9 万；不是大数据问题。

既有存储形态：CSV 日线（App 热路径 stdlib 读）+ 已有 SQLite（storage/kss_quotes.db、intraday_quotes.db、ledger 等）+ parquet（ETF 回测）+ JSON 归档（paper_trade / bj50_scan）。kss/data/sqlite_store.py 自述为「CSV 的可选加速通道，旧路径保留」。

App 约束：snapshot / stock 热路径故意避 pandas、避网络；数字纪律要求真值来自本地产物。

Past learnings：PIT 分钟层方案已在 docs/solutions/pit_versioned_intraday_data_layer.md；包装 ideation 已点名 path/state 分离；agent 框架 ideation 要 data catalog，而非「先上库再说」。

本次 grounding 主要来自会话内故障复盘 + 仓库扫描；未另开外部调研（问题边界清楚）。

Topic Axes

  • A1 抗冲盘 / 运维安全 — checkout、clone、工作区脏状态
  • A2 新鲜度契约 — 图表 / 纸交易结算 / 扫描「最新可交易日」是否可观测、可告警
  • A3 App 读路径 — stock history、snapshot 列表、热启动成本
  • A4 多消费者一致 — 日更、paper settle、复盘、北证、回测是否读同一真源
  • A5 迁移与复杂度 — bridge 零 pandas、并发 writer、bundle 体积

Ranked Ideas

1. 现象≠上库：运维层先做完 2. 新鲜度契约 + 脏数据 UI 3. 双写轻 SQLite 读副本 4. State-root 单仓，与 git 根物理分离 5. 按资产分层存储 6. 统一 quotes 表 + catalog 门面 7. 拒绝：为这次事故全量迁库
#1 · Conf 92% · Complexity Low

现象≠上库：把「抗冲盘」做完再谈架构

axis: A1 抗冲盘 · frame: assumption-breaking

这次失败的充分原因是「被跟踪的运行态文件」。脱钩 + gitignore（PR #58）后，checkout 已不再抹日更。数据库解决不了「人把真源提交进 git」的流程问题——SQLite 若误入库同样会被冲。

basis direct: 会话复盘：日更到 7 月后 git checkout -f 还原 tracked csv；脱钩后 tracked=0 且 checkout 保留 2026-07-10 末行。

rationale：先分清「事故类型」：运维/版本控制 vs 存储引擎。错误归因会浪费一个季度做迁库。

downsides：看起来「不够架构」；新人仍可能 git add -f 强制入库。

#2 · Conf 88% · Complexity Low–Med

新鲜度契约：末日期门禁 + 自选图「数据日」徽标

axis: A2 新鲜度 · frame: pain / leverage

无论 CSV 还是 SQLite，缺的是产品级新鲜度：stock 详情顶栏显示 latestDate；若 today−latestDate ≥ N 交易日，徽标「日线陈旧 · 去刷新」并链到 Runbook update-cs-data。纸交易结算同口径（已有 stale_gap 日志，未进 UI）。

basis direct: bridge stock 已返回 latest.latestDate；update_cs_data 已写 update_cs_data_last.json stale_gap ALERT，但 App 自选图不展示。

rationale：用户感知的是「停在 6 月」，不是「引擎是 CSV」。可观测性比换存储更能防复现。

downsides：不提升查询性能；交易日历边界要小心（休市日）。

#3 · Conf 78% · Complexity Med

日更双写：CSV 保留 + SQLite 读副本（复用 SQLiteStore）

axis: A3 读路径 / A4 一致 · frame: leverage

update_cs_data 成功写 CSV 后 INSERT OR REPLACE 进 storage/kss_quotes.db。App stock history 优先 SQLite（按 ts_code 索引），失败回落 CSV。不改 cron 语义、不强制一次性迁移。

basis direct: kss/data/sqlite_store.py 已声明「CSV 可选加速、schema 对齐、stdlib sqlite3」；storage/kss_quotes.db 已存在。

rationale：若下一痛点是「全池扫描慢 / 多票 join」，再上库有现成落点；双写降低风险。

downsides：双写漂移；App 热路径若引 pandas 会违 bridge 约束（需纯 sqlite3 读）。

#4 · Conf 80% · Complexity Med

State-root 与 git 根物理分离（默认 Application Support）

axis: A1 抗冲盘 · frame: inversion

即使 CSV 脱钩，开发机仍常在 clone 根写 cs_data_*。打包路径已有 KSS_STATE_ROOT；统一默认：日更与 App 都写 ~/Library/Application Support/KSS/，repo 只剩代码。git 操作物理上碰不到真源。

basis direct: bridge STATE_ROOT = KSS_STATE_ROOT or PROJECT_ROOT；breadcrumb 曾指向 repo；包装 ideation 已痛「storage 相对仓库」。

rationale：防御深度：gitignore 是约定，分离是物理隔离。

downsides：迁移旧 clone 数据；cron/plist 要改路径；调试时要知道「数据不在仓库旁」。

#5 · Conf 74% · Complexity Med–High

按资产分层：日线 CSV、分钟 SQLite、归档 JSON/parquet 不动

axis: A5 迁移 · frame: constraint-flipping

不「全库统一」。日频池子小 → 保持 CSV（或双写）。高频/版本化 → 继续 PIT 分钟 SQLite（已有方案）。扫描/纸交易 → JSON 审计底稿可保留。拒绝 one-size-fits-all 数据库。

basis direct: pit_versioned_intraday_data_layer.md 已说明日频 SQLiteStore 不能承担分钟 PIT；多形态已在 storage/ 并存。

rationale：KSS 的痛点是语义分层（PIT / 前向 / 审计），不是「少一种文件格式」。

downsides：心智负担多源；catalog 必须跟上（否则 agent 仍猜）。

#6 · Conf 65% · Complexity High

统一 quotes 表 + data_catalog 门面（中长期）

axis: A4 一致 · frame: cross-domain / leverage

当出现「多池扩张到千票、跨表 join、服务化读」时：统一 (ts_code, trade_date) 表、writer 仅日更、reader 仅 catalog/bridge。配合已有 storage/data_catalog.json 刷新。

basis external: 量化平台常见「文件落盘 + 库内查询」分层；direct: agent ideation 已要 catalog 列级字典。

rationale：这是增长触发的架构，不是今天事故的修复。

downsides：全量读路径改造；与「bridge 无 pandas」张力；回测脚本大面积改动。

#7（显式否决项）· Conf 90%

「立刻把日线全迁数据库，替换 CSV」——不推荐作为本现象的回应

axis: A5 · frame: pain（误诊）

全量迁库不解决 git 误跟踪；14MB 池子上性能收益弱；违反「最小改动 + 热路径简单」；已有 sqlite_store 未成为默认读路径说明优先级本就不高。

basis reasoned: 根因已由脱钩验证消除；迁库成本 ≫ 本事故复发概率（若坚持 no-add 政策）。

若强行上：延期真正需要的新鲜度 UI 与 state-root 分离。

Rejection Summary

砍掉的方向原因
Postgres / 远程 DB单人桌面工作台；违背本地优先与热路径简单；overkill
只用 parquet 替代全部 CSVApp 热路径避 pandas；与 bridge 约束冲突
把 paper_trade/bj scan 也立刻入库审计底稿要可读 JSON；与本次图陈旧无关
「再跟踪一份种子 CSV」重蹈覆盖；与 #1 矛盾
为 agent 单独再做一个向量库存行情subject overrun；行情不是语义检索问题
