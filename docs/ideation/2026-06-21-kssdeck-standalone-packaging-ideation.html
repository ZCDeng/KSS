Grounding Context（Codebase Context）

当前 KSSDeck 是一个只读的瘦 SwiftUI 前端，架在一个 Python 产物仓库之上 —— 它不是自包含的。这套设计在「开发者本机跑」的场景非常顺手，但要变成一个能发给别人、能持续演进的独立 app，缺口集中在两件事：Python 运行时与依赖不在 bundle 里、数据路径绑死在仓库根。

  • 桥：BridgeClient.swift:108 每次调用都 Process 拉起 /usr/bin/python3 跑 scripts/kss_app_bridge.py，cwd=projectRoot，返回 JSON（AppSnapshot ~80KB，逼近 64KB pipe buffer，已用并发读绕开死锁）。
  • 路径：findProjectRoot() 向上爬 ≤8 层找脚本；storage / cs_data / kss/config 全是仓库相对 → app 必须活在 clone 里，进不了 /Applications。
  • 调度：crontab 8 个工作日 job + 一个未 bootstrap 的 launchd selfcheck 看门狗；in-app「N 个任务漏跑」横幅 + 一键 catchup 已存在。
  • AI：板块 commentary 走 Claude API → 写死的静态 .md 进 storage，app 读 Markdown 渲染；LLM 数字必须代码渲染（幻觉防线，靠 prompt 不靠结构）。
  • 打包：build_and_run.sh 出 dist/KSSDesktop.app（~8MB，无 codesign）；Python 运行时假定本机存在。

核心张力：今天改 Python 不用重编译（小时级快迭代）；天真打包会反转这个性质。「可进化 vs 可分发」直接冲突 —— 必须显式设计混合方案，而不是二选一。这条张力是下面多数 idea 的共同锚点。

QuantDinger 参照核验：它是 Docker SaaS（Vue+Flask+PG+Redis），打包/分发层几乎不可借鉴。可借的只有三样 —— ① MCP server 包住 CLI（它在 PyPI 发了 quantdinger-mcp）；② paper-only-by-default 安全闸；③ research→backtest→paper→live 晋升流心智模型。

01

可重定位运行时 + state root 分离

ax1 运行时打包Conf 88%Cx High

P0 地基。用 py-app-standalone（uv 可重定位 env）把 Python 3.12 + 全部依赖 vendored 进 Contents/Resources/python-env/，BridgeClient.swift:108 的 /usr/bin/python3 改成 bundle 内路径（一行）；requirements.lock 锁死可复现性（解掉 pyarrow 手装问题）。同时把不可变 bundle 代码与可变状态拆开：KSS_STATE_ROOT 默认 ~/Library/Application Support/KSS/，安装脚本写一个 breadcrumb，findProjectRoot() 8 层上爬退化成「脚本恒在 Bundle.main.resourcePath」。把网络依赖（Tushare key / TELEGRAM_API_URL / 代理）一并表面化为可见配置，缺数据时大声降级而非静默失败。

Basis
directBridgeClient.swift:108 硬编码 /usr/bin/python3、:143-168 8 层上爬；kss_app_bridge.py:25 PROJECT_ROOT=parents[1]；external py-app-standalone = solo-dev 最佳；XDG state-root 惯例。（verifier: sound，证据全部核实）
Rationale
这是「别人能装」的字面前提。不做这一条，签名、Sparkle、第二台机器安装全部无意义 —— 干净机器上 app 立刻 fail。bundle=不可变代码 / state root=可变数据这条不变量也让签名 bundle 可写状态成为可能。
Downsides
最大工作量（vendoring + 路径重构 + 安装/迁移脚本）；一次性迁移已有 storage/；bundle 体积从 8MB 涨到数百 MB。
02

常驻 Python sidecar（Unix socket）

ax2 桥接进程Conf 85%Cx Medium

把「每次调用 fork 一个 python3、重 import pandas、~80KB 过管道」换成启动时拉起一次的常驻进程，Swift 用行分隔 JSON 走 ~/Library/Application Support/KSS/ 下的 Unix domain socket，SMAppService / LaunchAgent 托管生命周期。pandas/pyarrow 冷启动只付一次，热路径降到纯 I/O；64KB pipe buffer 死锁风险彻底消失。

Basis
directBridgeClient.swift:105-141 subprocess-per-call + :119-122 代码注释自述 80KB/64KB 管道死锁绕行；external Tauri sidecar / SMAppService 同构模式。（sound）
Rationale
同时干掉冷启动延迟与脆弱的双管道补丁，并且这个 socket 接口正是 idea 4（MCP）的天然挂载点 —— 「快 app」和「可被 agent 调用」收敛到同一个面。
Downsides
引入进程生命周期/崩溃重启/僵尸清理的复杂度；需要 socket 超时回退到 subprocess 的兜底。
03

版本化桥协议（schemaVersion 信封）

ax2 桥接进程Conf 86%Cx Small

每个 bridge 响应顶层加 schemaVersion 信封 + Swift 端 negotiator（版本不匹配时降级/迁移，而非崩）。退役 HotspotLeaderStock 那个手缝双 schema 兜底解码器；不匹配时给「请更新 app / 脚本」的可读横幅，取代静默的 Bridge returned invalid JSON。

Basis
directKSSModels.swift:25-62 双 schema fallback decoder，注释明写 "Bridge returned invalid JSON"；全仓库 grep 无 schemaVersion；external DB schema migration 的 versioned-envelope 模式。（sound）
Rationale
一旦 Swift 与 Python 真正独立发版（idea 6），无版本号的 payload 必然产生更多静默解码崩溃。现有的双 decoder 是警告弹；版本信封是阻止你手写第三个 decoder 的系统。成本最低、收益清晰。
Downsides
需要一次性给所有现存命令补字段；negotiator 的迁移分支需要测试覆盖。
04

kss-mcp：把桥包成 MCP server（AI-native 基石）

ax5 AI-nativeConf 84%Cx Medium

把现有 bridge 命令集（snapshot / stock / sector-rotation / run / report / cron-*，~15-25 个）包成一个本地 MCP server（stdio），paper-only 默认（实盘/写操作需显式 flag）。同一套逻辑面同时服务 SwiftUI app 和外部 agent —— 常驻 sidecar（idea 2）一个进程开两个接口。这是把 commentary 从「AI 写死 .md，app 读」翻转成「agent 可以主动查实时数据、跑回测、生成提示」的关键一跃，也是全场最强收敛：5 个 frame 全部独立指向它。

Basis
external QuantDinger quantdinger-mcp（PyPI，REST→agent tools）+ paper-only-by-default 闸，均标记 TRANSFERABLE；direct bridge 命令集已是天然 tool surface。（sound）
Rationale
每新增一个桥命令都零边际成本地同时成为 agent 能力。把 KSS 从「我看的工具」升级成「agent 可操作的工作站」，安全闸直接整套借用参照架构。CLAUDE.md「模型只做判断、确定性让代码答」与之同向。
Downsides
写操作的权限边界必须严格（paper-only 闸是硬要求）；MCP SDK 依赖需进 vendored env。
最高杠杆的战略下注
idea 2 + 4 合起来是「一个常驻 daemon、两个接口」—— 它既解决性能/死锁，又是 app「AI-native」的本体。若只能先做一件能改变路线的事之外的第二件，是这个。
05

签名 + 公证 + CI 流水线

ax3 分发签名Conf 72%Cx Medium

Developer ID codesign + xcrun notarytool + GitHub Actions full-Xcode runner：push tag → 构建 → 签名 → 公证 → 生成 appcast。移除 Gatekeeper 首次启动那道「身份不明开发者」墙 —— 这是从「开发者工具」变成「可发给别人的产品」的唯一门票。

Basis
directbuild_and_run.sh 全文零 codesign；institutional memory：本机 CLT 无 XCTest，codesign/notarize 需 full Xcode；external Sparkle generate_appcast + GHA Release 配套。（sound）
Rationale
手工发版 = 「懒得发就不发」。自动化 CI 把发版从「有空才做」变「改完就出」，也是 Sparkle 自更新能跑的前提。
Downsides
需 $99/年 Developer ID 与 keychain 在 CI 的密钥管理（Fastlane match）；本机 CLT 跑不了，依赖 GHA full-Xcode runner。信心 72% 因为这两个外部前提不在代码控制内。
06

双通道演进：Sparkle + 独立 Python 层

ax4 可进化回路Conf 75%Cx Medium

Swift 二进制走 Sparkle（appcast + BinaryDelta delta）；Python 层走独立通道 —— 启动时 uv sync --frozen 对比 lock，或 manifest 拉 python-env.tar.gz 两槽原子替换。两层版本号解耦：改一个桥命令不必重签整个 .app。这是消解「可进化 vs 可分发」张力的那一刀 —— 保住「改 Python 不重编」的核心 DX 资产。

Basis
external Sparkle（indie macOS 自更新标配，appcast/BinaryDelta/SUFeedURL）；direct grounding 明列的 TENSION + kss-desktop-packaging-deferred memory；reasoned 签名 bundle 上 Resources-only 改动免重新公证。（sound）
Rationale
Python 层迭代频率 ~10× 于 Swift UI。解耦让一个 schema 修复几分钟内经 manifest 出货，而非排队等完整 Xcode 构建 + 公证。
Downsides
两层版本可能 desync 成坏组合 —— 需配合 idea 3 的版本协议 +（可选）两槽回滚；on-launch 网络更新要静默且可失败。
07

AI-native commentary 深化：结构化 + 决策账本

ax5 AI-nativeConf 82%Cx Small-Med

三个互补动作：(a) 结构化 commentary —— LLM 只输出 null/定性标签，代码在 render 时从 parquet/CSV 填真值（JSON 而非静态 .md，幻觉防线从 prompt 自律变成类型系统约束）；(b) commentary 存为可查询的 sqlite 线程，支持追问；(c) append-only 决策账本（snapshot hash + commentary 引用 + 当日 prediction）喂 eval/feedback 回路。

Basis
direct commentary = 静态 .md（grounding）+ llm-numbers-deterministic-rendering memory（龙虎榜幻觉实证）；external QuantDinger append-only audit log。（sound，机构 grounding 最强、改造成本最低）
Rationale
写死的 .md 是「AI-native」app 里最静态的东西 —— 答不了追问。把确定性数字（列）与 prose（列）分开，既保住已验证的幻觉防线，又解冻交互；账本给 eval 回路一个可回放的黑匣子（「那天 commentary 说对了吗」从无法回答变成一个 query）。
Downsides
commentary 生成管线与 schema 都要改；(b)(c) 相对 (a) 是增量，可分期。
